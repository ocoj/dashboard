## i18n 代码操作规范（必须遵守）

本项目使用 `next-intl` v3 作为国际化框架，所有代码操作必须符合以下规范。

### 1. 命名空间规则

- 每个翻译 key 必须归属于正确的命名空间（`peers`、`dns`、`common`、`settings` 等）
- 在 `en.ts`/`zh.ts` 中，命名空间以大括号包裹的顶级 key 标识：
  ```ts
  peers: {       // ← 命名空间 "peers"
    addPeer: "添加节点",
    ...
  },
  ```
- **插入新 key 前必须先确认当前命名空间**：
  ```bash
  awk 'NR<行号{ns=$1} NR==行号{print ns}' zh.ts
  ```
- 不同模块的 key 严禁混入同一命名空间

### 2. Key 命名规范

- 使用驼峰命名：`addPeer`、`searchPlaceholder`、`editPeerNameDescription`
- 保持与已有 key 的风格一致（动宾结构优先）
- key 名应自解释，长度适中

### 3. 组件中引用规范

- 函数式组件内统一使用：
  ```tsx
  const t = useTranslations("命名空间");
  ```
- JSX 中使用：
  ```tsx
  <div>{t("keyName")}</div>
  ```
- 带动态参数：
  ```tsx
  t("keyName", { count: 5, name: peer.name })
  ```
- 复数形式（next-intl 内置）：
  ```tsx
  t("nPeers", { n: count })
  ```
- Placeholder 必须做 fallback，禁止硬编码：
  ```tsx
  placeholder={placeholder ?? t("searchPlaceholder")}
  ```
- **禁止**形如 `t("命名空间.key")` 的调用 — `useTranslations` 已绑定命名空间

### 4. 禁止行为（红线）

| ❌ 禁止 | ✅ 正确做法 |
|---------|------------|
| 在 .tsx 中硬编码英文/中文字符串 | 全部提取为 i18n key，用 `t()` 引用 |
| 用 Python 脚本序列化翻译文件 | 用 `sed` 直接插入单行 |
| 在不同组件中重复定义相同文案 | 提取到 `common` 命名空间复用 |
| `useTranslations()` 不传命名空间参数 | 始终显式指定命名空间 |
| 复制粘贴整个翻译文件后手动改 | 只新增/修改必要的 key |

### 5. 新增 key 的标准操作流程

```
Step 1: 确认归属命名空间 → awk 验证
Step 2: en.ts 对应位置插入英文 key → sed 插入（4 空格缩进）
Step 3: zh.ts 完全相同的命名空间/位置插入中文翻译 → sed 插入
Step 4: 组件中引入 useTranslations + t() 调用
Step 5: tsc --noEmit 验证 + grep 扫遗漏
```

### 6. 代码复查清单

每次汉化完成后逐项检查：
- [ ] 所有用户可见文本是否已用 `t()` 包裹？
- [ ] 是否使用了正确的命名空间（无串区）？
- [ ] `en.ts` 和 `zh.ts` 是否同步新增了对应 key？
- [ ] 组件中是否有残留的硬编码字符串？
- [ ] `npx tsc --noEmit` 是否零错误通过？
- [ ] 浏览器控制台是否无 `MISSING_MESSAGE` 输出？

## 标准工作流（严格按此顺序执行）

---

### 第 0 阶段：前置准备

1. 阅读本项目汉化工作流标准文档 `docs/SESSION_WORKFLOW.md`，了解完整流程
2. 阅读踩坑记录 `i18n/README.md`，避免已知问题
3. 熟记术语表 `i18n/TERMS.md`，保持翻译一致性
4. 确认本地开发环境正常：
   ```bash
   npx tsc --noEmit 2>&1 | grep -v "node_modules/@types/node" | grep -v "Cannot find"
   npx next build
   ```

---

### 第 1 阶段：检查上游更新

1. 切换到 `i18n-clean` 分支，确保工作区干净
2. 获取上游最新代码：`git fetch netbirdio`
3. 比较差异，评估变更量：
   ```bash
   git log --oneline i18n-clean..netbirdio/main
   git diff --stat i18n-clean..netbirdio/main
   ```
4. **无新提交** → 终止，报告"上游无更新"
5. **有新提交** → 记录变更摘要（涉及的文件范围、新增组件、新功能点），继续下一步

---

### 第 2 阶段：合并上游代码

1. 合并取上游版本：
   ```bash
   git merge netbirdio/main -X theirs --no-edit
   ```
2. 检查冲突：`git diff --name-only --diff-filter=U`
3. 手动处理残留冲突（取上游代码 + 重新添加汉化 `useTranslations`/`t()` 调用）
4. 编译检查：
   ```bash
   npx tsc --noEmit 2>&1 | grep -v "node_modules/@types/node" | grep -v "Cannot find"
   ```

---

### 第 3 阶段：全面汉化增量内容（核心环节）

> 本阶段严格遵循项目标准汉化工作流：**浏览器遍历 → 代码扫描定位 → 执行汉化 → 代码复查**

#### 3a. 浏览器遍历 — 记录所有英文文本

> ⚠️ **本步骤必须在真机/浏览器上完成，不可跳过。** 仅靠代码分析无法发现所有遗漏。

1. **部署当前代码到 OMV**（见第 6 阶段），或启动本地开发服务器
2. 打开 `https://nb.lanxun.pro:30443`，强制刷新（Ctrl+Shift+R）清除缓存
3. 切换到中文（右上角「选择语言」或 cookie `NEXT_LOCALE=zh`）
4. **逐菜单遍历**新增/变更的功能页面：
   - 点开每个子页、按钮、Tab、弹窗
   - 弹窗内每个 Tab 都要点击，每个表单字段、下拉选项、placeholder 都要查看
   - 多步向导要正常填写信息推进到下一步，检查每一步
   - 按钮悬停提示（tooltip）也要检查
5. 浏览器控制台搜索 `MISSING_MESSAGE` 找缺失翻译
6. **记录所有发现的英文文本**，形成完整清单

#### 3b. 代码扫描定位

1. 列出本次合并新增/修改的文件（排除翻译文件自身）：
   ```bash
   git diff --name-only --diff-filter=AM HEAD
   ```
2. 对每个新增/修改的 `.tsx` 文件，搜索硬编码英文：
   ```bash
   grep -rn ">[A-Z][a-z]" 文件路径 --include="*.tsx" | grep -v "useTranslations\|t(\|className\|href\|<Icon\|\.tsx"
   ```
3. 对照浏览器遍历的记录清单，逐一定位源文件和行号
4. 分类处理：
   - **缺 i18n key 的文本** → 需新增 key
   - **有 key 但 zh.ts 未翻译** → 直接补充翻译
   - **硬编码在 .tsx 中的英文** → 引入 `useTranslations()` 替换

#### 3c. 执行汉化（严格遵循 i18n 代码操作规范）

严格按照上方 **「i18n 代码操作规范」** 执行，重点如下：

1. **确认命名空间** — 插入前用 `awk` 验证当前 key 归属的命名空间
2. **同步增删 key** — `en.ts` 和 `zh.ts` 必须保持结构一致、key 顺序一致
3. **组件硬编码修复** — 引入 `useTranslations("命名空间")`，所有显示文本替换为 `t("key")`
4. **Placeholder fallback** — 使用 `placeholder ?? t("keyName")` 模式
5. **禁止行为** — 不允许任何硬编码字符串残留在 .tsx 中
6. **翻译规范**：
   - 中文引号用「」，避免 TS 字符串中转义
   - 参考 `i18n/TERMS.md` 术语表
   - 保持与已有翻译风格一致

#### 3d. 代码复查

1. TypeScript 编译检查：
   ```bash
   npx tsc --noEmit 2>&1 | grep -v "node_modules/@types/node" | grep -v "Cannot find"
   ```
2. 对本次涉及的所有组件目录，做硬编码英文兜底搜索：
   ```bash
   git diff --name-only HEAD | xargs -I{} dirname {} | sort -u | \
     xargs -I{} grep -rn ">[A-Z][a-z]" {} --include="*.tsx" 2>/dev/null | \
     grep -v "useTranslations\|t(\|className\|href\|<Icon\|\/\/"
   ```
3. 对照复查清单逐项确认（见 i18n 规范第 6 节）
4. 补遗漏 → 再 tsc → 循环至零错误 + 零遗漏

---

### 第 4 阶段：构建验证

1. 完整静态导出构建：
   ```bash
   npx next build
   ```
2. 确认 `out/` 目录生成成功，无构建报错

### 第 5 阶段：发布新版本

1. 更新版本号（上游版本 + `-zh`，如 `v2.91.0-zh`）
2. 更新 `CHANGELOG.md`，记录本次同步的变更摘要
3. 创建 Git tag：`git tag v2.91.0-zh`
4. 提交并推送：
   ```bash
   git add -A
   git commit -m "sync: 同步上游至 v2.91.0 + 汉化"
   git push origin i18n-clean
   git push origin v2.91.0-zh
   ```
5. GitHub Actions 自动构建 Docker 镜像：
   - Push tag → `ghcr.io/ocoj/dashboard:v2.91.0-zh`
   - Push i18n-clean → `ghcr.io/ocoj/dashboard:latest`

1. 通过 Vaultwarden MCP 获取 OMV SSH 密码（关键字：`omv ssh`）
2. 执行远程部署（**只拉取新镜像，不修改任何配置**）：

### 第 7 阶段：真机验证闭环（必须）

> ⚠️ **此阶段为汉化质量的最终确认，不可跳过。** 所有汉化必须经过真机确认才算完成。

1. 打开 `https://nb.lanxun.pro:30443`，强制刷新（Ctrl+Shift+R）清除缓存
2. 切换到中文（右上角「选择语言」或 cookie `NEXT_LOCALE=zh`）
3. **逐项遍历**本次变更涉及的所有页面：
   - 页面标题、描述文本
   - 导航侧栏菜单项
   - 表格列头、数据行、空状态提示
   - 弹窗/Modal 每个 Tab
   - 表单字段标签、placeholder、下拉选项
   - 按钮文字、Tooltip 悬停提示
   - Toast 通知
   - 多步向导每一步
4. 浏览器控制台搜索 `MISSING_MESSAGE`，确认无缺失翻译
5. 对比第 3a 步的记录清单，逐条确认已修复
6. **有遗漏** → 记录遗漏清单 → 回到第 3c 步修补 → 重新构建发布 → 再次真机确认
7. **全部通过** → 汉化完成 ✅

## 常见踩坑速查

| 坑 | 对策 |
|----|------|
| 合并冲突 | `git merge -X theirs` 取上游，事后补汉化 |
| 反斜杠加倍 | 禁止 Python 序列化翻译文件，用 `sed` 直接插入 |
| 行号偏移 | 每次 `sed` 后先 `grep` 确认目标行 |
| 命名空间串区 | 插入 key 前用 `awk` 确认当前 namespace |
| 浏览器缓存 | 部署后 Ctrl+Shift+R 强制刷新 |
| key 找不到 | 浏览器控制台搜 `MISSING_MESSAGE` 定位 |
